# crm/opportunity 的设计

本页写这个组件为什么这样设计：术语、拥有的数据、状态、规则要点、命令与事件、依赖、实现状态与未决问题。写给要修改它的人与 AI。怎样使用、部署与配置在 `BRICKKIT.md`；代码在哪、怎样构建与测试在 `AGENTS.md`。

跨组件的规则在装配项目：引用与资格在协议 07，投影在协议 02，单号与金额在协议 14，列表与搜索在协议 13，数据范围在安全 07；决定 A71（商机请求报价，销售生成带商机参考的报价，报价与订单的事件带商机参考回到商机）。端到端的位置见装配项目的业务流程“订单到收款”的第 1 步。首批范围是装配项目阶段计划 C6 的 P0 定的（AI 定，待复核）。

## 边界

商机：一笔可能成交的生意，从发现到赢单或输单；它的阶段、阶段历史、预计金额与概率，以及按阶段加权的预测（漏斗）。CRM 与 ERP 之间没有同步调用，只经事件协作（边界卡）。

| 不在这里 | 归谁 |
| --- | --- |
| 报价与订单本身（价格、税、明细的校验、预占） | `erp/sales`（消费本组件的“请求报价”，生成带商机参考的报价草稿；它的报价与订单事件带商机参考回到本组件） |
| 客户的身份、正式联系人 | `mdm/partner`（本组件只引用客户角色，取资格） |
| 客户关系的负责人、公海、共享 | `crm/customer`（远期；缺时商机的负责人就是本组件自己的字段，缺省创建人） |
| 线索与转化 | `crm/lead`（远期） |
| 拜访与跟进的记录 | `crm/activity`（远期） |
| 法人、币种 | `mdm/org`、`mdm/currency` |

## 术语

| 业务叫法 | 定义 | 代码标识符 |
| --- | --- | --- |
| 商机 | 某法人对某客户的一笔可能成交的生意：名称、币种、预计金额、预计成交日、负责人、阶段、概率、可选的产品明细 | `opportunity` |
| 阶段 | 商机在管道里的位置。首批一条固定管道：进行中的 `qualification`（资格确认）、`needs_analysis`（需求分析）、`proposal`（方案报价）、`negotiation`（谈判），终态 `won`（赢单）、`lost`（输单） | `stage` |
| 概率 | 成交的可能性，0–100 的整数；进行中的阶段有缺省值（10、25、50、75），可以改；赢单 100，输单 0 | `probability` |
| 加权金额 | 预计金额 × 概率 / 100，预测与漏斗用它 | `weighted_amount`（查询里算，不存） |
| 阶段历史 | 每次阶段变化一行：从、到、原因、谁、何时 | `stage_change` |
| 产品明细 | 请求报价时给销售预填的建议：产品、数量、单位；本组件不校验产品，销售生成报价时校验 | `opportunity_line` |
| 请求报价 | 请销售按这个商机生成报价草稿；本组件发布事实，销售消费 | `quote_request`；事件 `crm.opportunity.quote_requested.v1` |
| 关联的销售单据 | 销售的报价与订单中带本商机参考的那些，按它们的事件记下（显示用） | `sales_link` |
| 自动赢单 | 部署方（边界卡与 A71 说的“客户”）的设置：报价被接受或订单被确认时，把关联的商机标为赢单 | 配置键 `OPPORTUNITY_AUTO_WIN`：`manual`（缺省）、`quotation_accepted`、`order_confirmed` |
| 重开 | 赢单或输单之后明确回到进行中，回到关闭前的阶段与概率 | `reopen` |

## 拥有的数据

| 表 | 内容 | 终态与保留 |
| --- | --- | --- |
| `opportunity` | 单号、法人、客户（与快照的名称）、名称、币种、预计金额、预计成交日、负责人、阶段、概率、关闭前的阶段与概率、关闭的原因与时间、赢单金额、搜索列、版本 | `won`、`lost` 可以重开；不删除 |
| `opportunity_line` | 产品、数量、单位、顺序 | 随商机 |
| `stage_change` | 商机、从、到、原因、操作者、时间、触发（`user` 或销售单据的身份） | 随商机，只追加 |
| `quote_request` | 请求身份（即事实身份）、商机、请求时的明细快照、状态 `requested`、`drafted`（销售生成了草稿：报价身份）、`rejected`（销售拒绝：原因）、操作者、时间 | 随商机 |
| `sales_link` | 商机、单据种类（`quotation`、`sales_order`）、单据身份、单号、状态、不含税合计与币种、最后看到的版本 | 随商机；按版本覆盖 |

以后还有：可配置的管道与阶段、部门的投影、扩展字段（协议 08）。

## 状态

每张表在代码里是同一张表（`core.Table`），单元测试逐格比较。表的状态是 `open`（四个进行中的阶段：它们在表里的格完全相同，阶段之间怎样走是 OP03 的事）、`won`、`lost`；新建不在表里（OP01：新建的商机是 `open`）。格的写法：`允许`（照常做，状态不变）、`拒绝`、`忽略`（什么也不做，照原样回答）、`→ <状态>`；格里效果之前的字是条件。

### 商机

| 命令 | `open` | `won` | `lost` |
| --- | --- | --- | --- |
| 修改 `edit` | 允许 OP02 | 只改名称与预计成交日时允许 OP02 | 拒绝 OP02 |
| 推进 `advance` | 目标是当前之后的进行中阶段时允许 OP03 | 拒绝 OP03 | 拒绝 OP03 |
| 回退 `revert` | 目标是当前之前的阶段、写明原因时允许 OP03 | 拒绝 OP03 | 拒绝 OP03 |
| 改负责人 `assign` | 允许 OP04 | 允许 OP04 | 允许 OP04 |
| 请求报价 `request_quote` | 允许 OP05 | 拒绝 OP05 | 拒绝 OP05 |
| 赢单 `win` | → `won` OP06 | 忽略 OP06 | 拒绝 OP06 |
| 输单 `lose` | 写明原因 → `lost` OP06 | 拒绝 OP06 | 忽略 OP06 |
| 重开 `reopen` | 忽略 OP07 | 写明原因 → `open` OP07 | 写明原因 → `open` OP07 |
| 销售单据到达 `sales_event` | 允许（记下；按设置自动赢单，走 `win` 的格） OP08 | 允许（只记下） OP08 | 允许（只记下） OP08 |

| 规则 | 内容 |
| --- | --- |
| OP01 | 新建：法人（向 `mdm/org` 取证：存在、活跃）、客户（向 `mdm/partner` 取资格，用途 `sell`，即该法人下的客户角色活跃；协议 07 的资格引用，在有效期内提交）、名称（1–200 字）、币种（向 `mdm/currency` 取证：存在、活跃；缺省法人的本位币）、预计金额（不为负，按币种的小数位，可以为 0）、预计成交日（可空）、负责人（主体；缺省创建人；指定别人要另有改负责人的操作 `crm.opportunity.assign`，否则普通销售能绕过 OP04）、阶段（进行中的一个，缺省 `qualification`）与概率（缺省阶段的值）、产品明细（0–100 行：产品身份、大于零的数量、单位；同一产品可以出现多次）；单号 `OP`（按法人与年，允许缺号，`OP-<法人代码>-<年>-<六位序号>`）；同一事务写阶段历史的第一行（从空到初始阶段）与完整状态事件。要 `Idempotency-Key` |
| OP02 | 修改按版本整份替换给出的字段（明细给了就整体替换）；阶段不经修改，只经推进、回退、赢单、输单与重开。进行中：名称、客户（重新取资格）、币种、预计金额、预计成交日、概率、明细。赢单之后金额已定（边界卡的不变量）：金额、币种、客户、明细与概率（赢单是 100）都拒绝 `WON_AMOUNT_LOCKED`，改要重开；名称与预计成交日不影响金额，仍可以改（AI 定，边界卡只锁金额）。客户之后被暂停或角色关闭，本组件不订阅伙伴，不会自己发现：下次修改客户时重新取资格，销售生成报价时由销售取它的资格。输单的不能改，要先重开。法人不能改（它是数据范围的维度；换法人另建商机） |
| OP03 | 阶段只按声明的顺序推进或明确回退（边界卡的不变量）：推进的目标是当前之后的进行中阶段，可以跨过中间的阶段（顺序不变，只是不在中间停留）；回退的目标在当前之前、写明原因；目标等于当前、或推进与回退的目标是 `won`、`lost`（它们只经赢单与输单）答 `STAGE_ORDER`。概率改为目标阶段的缺省，命令里给了就用给的（手工改过的概率不带过去）。每次变化一行阶段历史、一个事实 `stage_changed` |
| OP04 | 改负责人：另一个操作（`crm.opportunity.assign`），给“销售主管”而不给普通销售；任何状态都可以（关闭的商机也要能交接）；审计 |
| OP05 | 请求报价：只在进行中。生成请求身份，同一事务里写 `quote_request`（`requested`，明细的快照：命令给了明细就用给的并同时替换商机的明细，否则用商机现在的）并发布事实 `crm.opportunity.quote_requested.v1`（事实身份 = 请求身份；带法人、客户、币种、负责人、商机的单号与名称、明细）。要 `Idempotency-Key`：同一键重放答同一个请求。请求是商机的一次变更：商机的版本加一、发完整状态事件、审计（操作 `crm.opportunity.edit`）。一个商机可以有多个请求（改了需求再要一张报价）。销售怎样生成草稿、哪些情形拒绝，归销售；本组件只记结果（OP08） |
| OP06 | 赢单：手动（`crm.opportunity.close`），可以给赢单金额（不给就用预计金额），概率变 100；输单写明原因，概率变 0；都记下关闭前的阶段与概率、阶段历史一行、事实 `won` 或 `lost`、审计。赢单金额与事实里的币种都是商机的币种。赢单的商机再赢单答成功、不再发事实；输单的商机要赢单先重开；重开之后再赢单或输单是新的一次关闭，照样发事实。关闭不碰已经发出的请求与销售那边的报价：要作废的报价由人在销售里取消 |
| OP07 | 重开：写明原因，回到关闭前的阶段与概率，清掉赢单金额与关闭的原因；阶段历史一行、事实 `stage_changed`、审计 |
| OP08 | 销售单据到达：订阅销售的报价与订单的完整状态事件，只取带商机参考、商机在本组件存在的（不存在的丢弃并记日志：可能是别的装配的商机身份，或伪造）；按单据身份与版本覆盖 `sales_link`（旧版本丢弃）；报价带请求身份的，把那个请求标为 `drafted`；销售拒绝请求的事实把请求标为 `rejected` 并记原因。自动赢单（设置不是 `manual`）：`quotation_accepted` 时报价变成 `accepted`、`order_confirmed` 时订单变成 `confirmed`，而商机在进行中 → `won`，赢单金额 = 那张单据的不含税合计（币种不同时用预计金额，并在阶段历史的原因里写明），操作者是本组件自己（订阅的处理没有用户，不做授权检查；阶段历史的操作者记 `system`，审计记录没有操作者），触发记单据身份；商机已赢单或已输单的只记下，不改状态（输单之后客户又下了单，由人决定要不要重开）。没有自动输单：报价取消、过期或订单取消都只记下（`quotation_accepted` 下赢单之后订单又取消，由人重开或改输单）。订单认出商机靠订单自己的商机参考（销售接受报价转订单时带过去），不经报价去推 |

拒绝的原因：状态不允许 `STATE_CONFLICT`；阶段顺序不对 `STAGE_ORDER`；赢单后改金额 `WON_AMOUNT_LOCKED`；客户没有资格时照资格查询的原因（`CUSTOMER_NOT_ELIGIBLE`，细节带 `role_not_opened` 等）；法人或币种不可用 `REFERENCE_INVALID`；主数据不可达 `DEPENDENCY_UNAVAILABLE`（什么也没改，可以重试）；版本不对 `VERSION_CONFLICT`；字段不合法 `REQUEST_INVALID`（SDK 的原因）。

## 规则要点

- **CRM 与 ERP 只经事件**：请求报价是本组件的事实，销售消费；销售的结果经它的报价、订单事件与“拒绝请求”的事实回来。本组件不调用销售，销售也不调用本组件，两边都不声明对方为依赖（只订阅：都声明会把精确版本互相钉住，任何一边发布都要另一边再发布，永远对不齐；订阅不需要依赖）。
- **事务里不调用别的组件**：法人、币种、客户资格在事务之前取证；资格在有效期内提交（协议 07）。
- **负责人是本组件的字段**：数据范围“销售只看自己的商机”按它；`crm/customer` 的负责人变化事件以后只用作新建时的缺省，不作授权维度（边界卡）。
- **预测**：首批按阶段概率加权；方法是替换点（Fork 时换掉 `forecast` 模块，查询的形状不变）。
- **事实在业务事务里发布**：阶段变化、请求报价、赢单、输单都与状态的改变在同一个本地事务里写发件表；完整状态事件按版本覆盖。

## 命令与查询

| 命令或查询 | 面 | 操作 |
| --- | --- | --- |
| 商机：列表（法人、客户、阶段、负责人、预计成交日的范围、搜索单号与名称；游标分页）、读取（带明细、阶段历史、请求报价、关联的销售单据） | 用户面 | `crm.opportunity.read` |
| 新建、修改、推进、回退、请求报价 | 用户面 | `crm.opportunity.edit` |
| 赢单、输单、重开 | 用户面 | `crm.opportunity.close` |
| 改负责人 | 用户面 | `crm.opportunity.assign` |
| 漏斗：按法人、币种、阶段的个数、金额合计、加权金额（每个有商机的法人、币种与阶段一行，没有商机的阶段不列；终态也列：赢单的金额用赢单金额，输单的加权为 0；加权金额按币种的小数位舍入，协议 14）；可按负责人、预计成交日的范围筛选；只算看得见的商机（首批没有受限字段，金额与概率对看得见的人都可读） | 用户面 | `crm.opportunity.read` |
| 整套恢复的核对（`CheckService`） | 系统面 | `crm.opportunity.system.recover`（只许恢复工具） |

资源 `crm.opportunity`，两个维度：法人（值集合）、负责人（主体）。首批没有部门维度：销售主管的授予是法人内的全部负责人（种子照这样授予）。新建与请求报价要带 `Idempotency-Key`。

## 事件

流 `crm.opportunity`：

| 事件 | 类型 | 形状 |
| --- | --- | --- |
| 商机 | `crm.opportunity.changed.v1` | 完整状态（不带阶段历史、请求与关联单据），按版本覆盖 |
| 阶段变化 | `crm.opportunity.stage_changed.v1` | 增量事实：商机、从、到、原因、触发 |
| 请求报价 | `crm.opportunity.quote_requested.v1` | 增量事实（事实身份 = 请求身份）：商机身份、单号、名称、法人、客户、币种、负责人、明细 |
| 赢单 | `crm.opportunity.won.v1` | 增量事实：商机、赢单金额与币种、触发（`user` 或销售单据） |
| 输单 | `crm.opportunity.lost.v1` | 增量事实：商机、原因 |

订阅（销售的流 `erp.sales`）：`erp.quotation.changed.v1`、`erp.sales_order.changed.v1`（带商机参考的）、销售拒绝请求报价的事实 `erp.quote_request.rejected.v1`。销售没装时流不存在，订阅不报错、只等待。

## 依赖

| 依赖 | 必需 | 用来做什么 | 缺时 |
| --- | --- | --- | --- |
| `mdm/partner` | 是 | 客户资格（用途 `sell`）与名称的快照 | 起不来 |
| `mdm/org` | 是 | 法人的证据（存在、活跃、代码、本位币、时区） | 起不来 |
| `mdm/currency` | 是 | 币种的证据与小数位 | 起不来 |
| 身份、授权 | 是 | 平台 | — |
| `infra/audit` | 否 | 赢单、输单、重开、改负责人的审计 | 只写本地日志 |
| `erp/sales` | 不声明（只经事件） | 消费请求报价；它的报价与订单事件回到商机 | 请求报价照样发布，没有人消费，请求停在 `requested`（没有超时与撤回：请求只是记录，不占任何东西）；赢单与输单手工照常 |

销售那边做的（`erp/sales` 3.0.50 起，它的设计 QR01–QR05；本组件的 OP08 依赖这些）：

- 订阅 `crm.opportunity.quote_requested.v1`，记下处理过的请求身份（按事实身份去重：重复投递只生成一张草稿）；
- 生成报价草稿：法人、客户、币种、负责人取请求的，部门留空；请求的明细作为草稿上的“请求的产品”（产品、数量、单位）给销售人员参考，由人补成带价格与税率的明细再发出（商机不知道价格与税率；报价发出时才要求明细齐全）；客户此时没有资格、或法人与币种不可用，不生成草稿，发布“拒绝请求报价”的事实（带请求身份与原因）；
- 报价带商机身份与请求身份，接受转订单时把商机身份带到订单；`erp.quotation.changed.v1` 与 `erp.sales_order.changed.v1` 带出它们。

边界卡的必需依赖原来只写了伙伴、身份与授权；法人与币种的证据是协议 07 与协议 14 对引用方的要求（新单据要取法人的证据，金额按币种的小数位），所以加上 `mdm/org` 与 `mdm/currency`（AI 定，待复核；装配项目的边界卡与组件索引已经写上）。

## 整套恢复之后

存在性与版本：商机（审计过的对象）。单号是允许缺号的序列，没有要登记作废的号。请求报价停在 `requested` 的，销售那边按事实身份去重，重新投递不会生成第二张草稿；销售的事件按版本覆盖关联单据，重放安全。两边的发件表与订阅照 SDK 的恢复做法（协议 15）各自补发与重收，本组件不另做“请求停在 `requested`、销售已有草稿”的核对：销售的报价事件一到就补上。

## 部署与替换

低负载，适合外壳。预测方法是替换点（`forecast` 模块）；管道与阶段以后做成配置。

## 验证故事

1. 请求报价的事件重复投递只生成一张报价草稿（销售按事实身份去重；L3）。
2. 销售没装时赢单正常完成（手工；集成测试里没有销售）。
3. 商机请求报价 → 销售的报价草稿带商机参考 → 发出、接受转订单 → 确认订单 → 设置为 `order_confirmed` 时商机自动赢单，赢单金额是订单的不含税合计（L3）。
4. 赢单后改金额被拒；重开之后可以改。
5. 普通销售只看到自己负责的商机，漏斗只算看得见的。
