## 2. 功能详解

- **本组件没有 TCC 编排包**——两条强依赖（`mdm/customer`/`mdm/product`）都是只读 `BatchGet`，没有需要撤销的远程写操作（不像 `erp-sales` 的 `Reserve` 那样是跨进程 TCC 的一步）。跨组件校验直接放在 `service.CreateOpportunity` 里：先 `fetchActiveCustomer`/`fetchActiveProducts` 校验+取快照，再调 `repo.CreateOpportunity` 落库，两步之间没有需要补偿的窗口。
- **claim-first 幂等统一走 `command_idempotency` 一张表**（`repo/repo.go` 的 `claimIdempotency`），`CreateOpportunity`/`UpdateOpportunity`/`ChangeStage`/`MarkWon`/`MarkLost` 五个写命令共用同一套 INSERT ... ON CONFLICT DO NOTHING → 真正的写 → finalize 流程。
- **起始阶段固定用 `sort_order` 最小的那个**（`repo/stage.go` 的 `firstStageTx`）——契约没有给 `CreateOpportunity` 留 `stage_id` 入参，建档即进漏斗第一格。
- **加权金额（`expected_amount × probability`）读时现算，从不落库**（`repo/opportunity.go` 的 `computeWeightedAmount`）——落库会漂移：改了金额或概率，历史行的加权值就该跟着变，不是"另一条独立需要同步维护的数据"。
- **阶段带默认概率，但允许手工覆盖**（设计计划 §9 第 4 条，✅ 已查证 Odoo 的语义）：`CreateOpportunity`/`ChangeStage` 的 `probability`/`probability_override` 都用 proto3 `optional`，让"没传"和"传了 0"可区分——0 也是一个合法的手工覆盖值。
- **`MarkWon` 是链路的扳机，也是唯一带下游财务影响的动作**（`repo/write.go`）：单事务内完成"状态转 WON + `probability` 强制置 100 + `won_at` 落库 + Outbox 写入"，`buildWonPayload` 按设计计划 §4.1 的字段表精确拼 payload——**`owner_id`/`dept_path` 两个字段最容易漏**，`erp-sales` 的 handler 跑在系统身份下没有 JWT，这两个字段是它唯一能拿到归属信息的地方。
- **`ChangeStage` 任意阶段间可自由跳转，只记历史，不做顺序/审批约束**（设计计划 §2.2、§8 的 R-4 判定：这条分歧判定为 Fork 点，不建族）——`opportunity_stage_history` 只增不改，`from_stage_id` 允许为空（本组件的写入逻辑只在真正 `ChangeStage` 时才写这张表，建档时的初始赋值不算"流转"）。
- **`event_outbox`/`event_inbox` 从建仓库起就带周分区维护循环**（`backend/internal/partition`）——这不是可选项：`infra-workflow` 建仓库时漏了这个循环，第 5 周起 `INSERT` 会因为找不到覆盖的分区直接失败（根 `docs/dev/实测踩坑记录.md` C12），本组件直接照抄 `erp-sales` 复用的判据，从第一次提交起就接好。⚠️ 本组件**没有**月分区维护循环——`opportunities`/`opportunity_items`/`opportunity_stage_history` 不分区（设计计划 §2、§7），量级比交易流水低一到两个数量级。
- **`UpdateOpportunity` 是全量替换语义，不是部分 PATCH**（同 `mdm-customer` `UpdateRequest` 的既有判据）：`name`/`expected_amount`/`expected_close_date`/`owner_id` 未变的字段由调用方原样带回；`version` 乐观锁，与库里不一致时返回 `ErrVersionConflict`。

## 3. 完整契约清单

**gRPC `crm.opportunity.v1.OpportunityService`**（9 个 rpc，见 `contracts/crm/opportunity/v1/opportunity.proto`）：

| rpc | 类型 | 幂等键 | 说明 |
|---|---|---|---|
| `CreateOpportunity` | 命令 | ✅ | 建档，起始阶段固定 sort_order 最小的那个 |
| `UpdateOpportunity` | 命令 | ✅ | 改名/金额/预计成交日/负责人，全量替换 + 乐观锁 |
| `ChangeStage` | 命令 | ✅ | 阶段推进，写历史，任意跳转 |
| `MarkWon` | 命令 | ✅ | ⭐ 链路的扳机：转 WON + 发 `crm.opportunity.won.v1` |
| `MarkLost` | 命令 | ✅ | 转 LOST，要求填原因 |
| `GetOpportunity` | 读 | — | — |
| `BatchGetOpportunities` | 读 | — | 防 N+1，只返回找到的 |
| `ListOpportunities` | 读 | — | 漏斗视图数据源，走 ScopeFilter |
| `ListStages` | 读 | — | 阶段是数据不是代码，前端阶段选择器/漏斗视图用 |

**REST**（见 `contracts/opportunity.openapi.yaml`，路径前缀 `/crm/opportunity/**`）：

| 路径 | 权限键 |
|---|---|
| `GET /opportunities` / `GET /opportunities/{id}` | `crm.opportunity.view` |
| `POST /opportunities` / `PATCH /opportunities/{id}` | `crm.opportunity.edit` |
| `POST /opportunities/{id}/stage` | `crm.opportunity.edit` |
| `POST /opportunities/{id}/win` | **`crm.opportunity.win`**（单独权限键，唯一有财务影响的动作） |
| `POST /opportunities/{id}/lose` | `crm.opportunity.edit` |
| `GET /stages` | `crm.opportunity.view` |

⚠️ `BatchGetOpportunities` 不暴露 REST——组件间协议，给 BFF 层 GraphQL Resolver 防 N+1 用。

**发布事件：** `crm.opportunity.won.v1`（核心，⭐ 见设计计划 §4.1 完整字段表）、`.lost.v1`（旁路）、`.stage_changed.v1`（旁路）。
**消费事件：** `mdm.customer.created.v1`/`.updated.v1`（维护 `customer_snapshots.name`）。⚠️ **不消费 `erp-sales` 任何事件**——§1.4 铁律。

详细字段与判据见设计计划 `docs/design/crm-opportunity.md`——那份是真相源，这里是速查表。

## 4. 数据模型

| 表 | 分区 | 唯一约束 | 说明 |
|---|---|---|---|
| `opportunities` | **不分区** | `id` 主键 | `dept_id`/`dept_path`/`owner_id` 是**创建时快照**；`status` 复用为业务状态列（OPEN/WON/LOST/CANCELLED），符合 §11.2.1 强制字段要求 |
| `opportunity_items` | 不分区 | `id` 主键 | 全部快照，不 join；`quoted_unit_price` 是报价快照供参考 |
| `opportunity_stage_history` | 不分区 | `id` 主键 | 只增不改，不需要 §11.2.1 的 created_at/updated_at/version/status 四件套，同 `sales_order_reconciliation_queue` 的既有判据，只留一个时间戳 |
| `opportunity_stages` | 不分区 | `code` 唯一 | 阶段是数据不是代码，迁移播种（`003_seed_stages.up.sql`） |
| `customer_snapshots` | 不分区 | `customer_id` 主键 | 只取 `name`——本组件不关心信用额度，那是 `erp-sales` 的事 |

另有全组件通用的 `event_outbox`/`event_inbox`（周分区）+ `command_idempotency`（不分区）。

**实测验证**（真跑在 `crm_opportunity` schema + 真实 PostgreSQL + 真实 NATS，非 mock）：`CreateOpportunity`/`ChangeStage`/`MarkWon`/`MarkLost`/`UpdateOpportunity` 的 claim-first 幂等、`MarkWon`**真的把事件推送到 NATS 总线**（不是只看 `event_outbox` 表里躺着一行——真订阅 `crm.opportunity.won.v1`、真跑 `besdk.StartOutboxPump`、真收到消息并核对 `owner_id`/`dept_path`/`customer_id` 字段）、`ChangeStage` 真的写历史 + 发 `crm.opportunity.stage_changed.v1`、`UpdateOpportunity` 的乐观锁冲突、`MarkWon`/`MarkLost` 对非 OPEN 状态的商机统一拒绝、周分区维护循环真机对着运行中的容器验证（分区数量前后对比）、消费 `mdm.customer.created.v1` 真订阅真发布真等待、`CreateOpportunity` 真的调 `mdm-customer`/`mdm-product` 的 `BatchGet` 校验客户/产品存在与状态（真机连进两个组件所在的 Docker 网络跑的，不是 mock 响应）、迁移连跑两次幂等、Docker 镜像自检（`/bin/sh` + `wget`）。

## 5. 开发

```bash
export TEST_PG_DSN="postgres://postgres:<密码>@localhost:5432/brickkit_test_db?sslmode=disable"
export TEST_NATS_URL="nats://localhost:4222"     # 可选，缺省走 nats.DefaultURL
go test ./... -race -count=1
```

跑测试前必须先用真的迁移工具把 `crm_opportunity` schema 建出来：

```bash
export DATABASE_USER=postgres DATABASE_PASSWORD=<密码> DATABASE_HOST=localhost DATABASE_PORT=5432 DATABASE_NAME=brickkit_test_db PG_SCHEMA=crm_opportunity
go run ./backend/cmd/migrate up
```

`backend/internal/service` 下的跨组件校验测试（`TestCreateOpportunity_真实校验客户与产品并取展示快照` 等）额外需要 `MDM_CUSTOMER_GRPC_ENDPOINT`/`MDM_PRODUCT_GRPC_ENDPOINT`（`http://host:port` 格式，同 `besdk.Endpoint()` 认的格式）指向真实跑起来的 `mdm-customer`/`mdm-product`——本地开发这两个组件的 gRPC 端口通常不对宿主机暴露（只有 HTTP 端口发布），需要在它们所在的 Docker 网络里跑测试二进制，或临时用 `docker network connect` 把测试容器接进那个网络。缺省两个环境变量都没设置时这组测试会优雅跳过，不会假装通过。

`repo_test.go`/`consumer_test.go`/`service_test.go` 用带时间戳的 `uniqueSuffix`/`uniqueID` 前缀构造 `idempotency_key`/`customer_id`/`product_id`，测试之间互不干扰；`e2eTestCtx()`（`service_test.go`）用 `besdk.ContextWithClaims` 造一个"已经过 `RequirePermission` 验签"的 ctx，`besdk.ScopeOf` 才不会 panic。

**回归测试重点**：`TestMarkWon_真实转WON且Outbox记录且事件真的发布到总线`——这条直接对应阶段三计划文档对 Task 13 的明文验证标准，断言不能只停在"`event_outbox` 表里有一行"，必须真的跑一次 `besdk.StartOutboxPump` 并从 NATS 收到消息。⚠️ 这条测试的消息匹配要按 `opportunity_id` 过滤而不是假设"收到的第一条就是我要的那条"——`crm.opportunity.won.v1` 是全部商机共用的 subject，其它测试（如 `TestMarkWon_已终态不能重复赢单`）会留下自己的 `PENDING` Outbox 行且从不清空，这是实现这条测试时真实撞到过的坑，不是假设性的风险。

## 6. 排障

| 症状 | 根因 | 修法 |
|---|---|---|
| `MarkWon` 之后 `erp-sales`（未来接上时）建出来的订单"我的订单"列表查不到 | `crm.opportunity.won.v1` 的 `owner_id`/`dept_path` 字段漏发或值不对——`erp-sales` 的事件 handler 跑在系统身份下没有 JWT，只能靠事件带 | 检查 `repo.buildWonPayload` 是否原样带出了 `Opportunity.OwnerID`/`DeptPath`；这两个值应该等于建档时从 `besdk.ScopeOf(ctx)` 派生的快照，不是运行时重新计算 |
| `event_outbox` 里堆积了很多 `PENDING` 但从来没被推送 | 没有起 `besdk.StartOutboxPump` 后台循环——单跑开发时用 `go run ./backend/cmd/server` 会自动起（`module.go` 的 `Start`），单元测试直接调 `repo.MarkWon`/`ChangeStage` 等函数不会触发推送 | 需要断言事件真的到达总线时，测试里手动起一次 `besdk.StartOutboxPump`（参考 `write_test.go` 的 `TestMarkWon_真实转WON且Outbox记录且事件真的发布到总线`） |
| 迁移跑到 `003_seed_stages` 报唯一约束冲突 | 迁移被重复执行且 `code` 唯一约束已经有种子数据——正常情况下 golang-migrate 会跳过已应用的迁移（`schema_migrations_crm_opportunity` 表记录版本），报这个错通常是状态表被手动清空过或直接对着已有数据裸跑 `psql < 003_seed_stages.up.sql` | 检查 `schema_migrations_crm_opportunity` 表；正常路径永远走 `./migrate up`，不要绕过迁移工具直接执行 SQL 文件 |
| `ChangeStage`/`MarkWon` 返回 `ErrOpportunityTerminal` 但商机看起来还是 OPEN | 大概率是并发的另一个写命令抢先把状态改了（`FOR UPDATE` 保证不脏读，但两个几乎同时到达的请求里后到的那个确实该失败），或者调用方持有一个过期的商机状态快照 | 重新 `GetOpportunity` 确认当前真实状态，不要重试同一个命令；这是设计行为不是 bug（同 `erp-sales`/`infra-workflow` 对已终态资源的统一策略） |
| `service` 包的跨组件校验测试全部 SKIP | 未设置 `MDM_CUSTOMER_GRPC_ENDPOINT`/`MDM_PRODUCT_GRPC_ENDPOINT`，这是刻意的优雅跳过，不是失败 | 需要真机验证这条路径时，编译一个 `CGO_ENABLED=0` 的静态测试二进制，跑在能解析这两个组件容器 DNS 名的网络里，把两个环境变量指向真实的 `http://<容器名>:<gRPC端口>` |
